# 2. Обратный прокси
Обычно Trilium публикуется в интернете за **обратным прокси (reverse proxy)**, который отвечает за терминацию TLS, предоставляет единую публичную точку входа и (при необходимости) позволяет размещать несколько экземпляров на одном домене. Сам Trilium продолжает работать по обычному HTTP на локальном порту, а прокси находится перед ним.

В этом разделе собраны руководства для конкретных прокси-серверов, а также общие настройки, которые применимы независимо от выбранного прокси.

## Применимо к любому прокси

Независимо от выбранного прокси убедитесь, что выполнены следующие условия:

*   **Перенаправление WebSocket-соединений.** Trilium использует WebSocket для синхронизации и мгновенного обновления интерфейса. Прокси должен передавать заголовки `Upgrade` и `Connection`, иначе клиент будет выглядеть загруженным, но никогда не получит обновления.
*   **Настройка доверенного прокси.** Это необходимо, чтобы Trilium видел реальный IP-адрес клиента (для ограничения частоты запросов, логирования и защищённых cookie), а не адрес прокси. См. <a class="reference-link" href="2.%20Reverse%20proxy/Trusted%20proxy.md">Доверенный прокси</a>.
*   **Терминация TLS на прокси.** См. <a class="reference-link" href="HTTPS%20(TLS).md">HTTPS (TLS)</a>.

## Размещение прокси аутентификации перед Trilium

В некоторых конфигурациях на уровне прокси добавляется **слой forward-auth / SSO** (Authelia, Authentik, oauth2-proxy или OIDC-плагин), требующий прохождения интерактивного входа для _каждого_ запроса.

Это **нарушает синхронизацию и первоначальную настройку**. Синхронизация — это автоматический межмашинный процесс, работающий в фоновом режиме без браузера, поэтому он не может пройти интерактивную проверку входа. Когда прокси перехватывает запрос синхронизации, он возвращает HTML-страницу входа вместо ожидаемого JSON, и клиент завершается с ошибкой вроде:

```
Sync failed: Request to GET https://trilium.example.com/api/setup/status failed,
error: Unexpected token '<', "<!doctype "... is not valid JSON

```

Есть два способа решить эту проблему:

*   **Предпочтительный способ — использовать встроенную аутентификацию Trilium.** Не закрывайте Trilium аутентификацией на уровне прокси. Trilium может сам аутентифицировать веб-интерфейс, в том числе через [OpenID Connect](Signing%20in%20with%20OpenID%20Connect.md). При этом конечные точки синхронизации будут работать со своей штатной аутентификацией.
*   **Исключить конечные точки синхронизации из аутентификации прокси.** Если аутентификация на уровне прокси необходима, исключите следующие пути из проверки forward-auth:
    *   `/api/setup/*`
    *   `/api/login/sync`
    *   `/api/sync/*`

> [!NOTE]
> Это безопасно: Trilium самостоятельно аутентифицирует эти конечные точки. Синхронизация использует HMAC-рукопожатие на основе общего секрета, а одноразовый запрос начальной настройки защищён паролем — поэтому их исключение на уровне прокси не открывает неавторизованный доступ к вашим данным.

Пример для Nginx, где `/auth` — ваша конечная точка forward-auth:

```
server {
    # ... TLS, server_name, etc. ...

    # Sync and setup endpoints authenticate themselves — skip forward-auth.
    location ~ ^/api/(sync|login/sync|setup) {
        auth_request off;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_pass http://trilium;
    }

    # Everything else goes through forward-auth.
    location / {
        auth_request /auth;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_pass http://trilium;
    }
}
```
